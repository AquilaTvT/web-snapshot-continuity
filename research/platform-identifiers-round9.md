# Identifier behaviour under rollback, restore and undelete: platform documentation audit

Retrieved: 2026-11-05; scope corrections added 2026-11-08. The audit records identifier surfaces and operation-specific effects of rollback, restore and undelete. Some entries identify historical objects or management events rather than a field bound to an unqualified current read; the distinctions below are required before applying the identity non-reactivation theorem.

Method (original frozen quote audit). Every source in the original ledger was downloaded on the retrieval date. Every archived quotation was checked verbatim, after whitespace and Unicode NFKC normalisation, against the local copy. All 257 quotes from 106 sources match. The JSON ledger (`platform-identifiers-round9.sources.json`, same directory) records each source's URL, the URL actually fetched (redirect target, Markdown variant or raw-source mirror), the SHA-256 of the local copy, and the quotes. Vendor prose was preferred. Where prose is silent, project source code or project test suites were used, and this is stated each time. No live experiments were run.

**Scope correction.** The paragraph above describes the original quote audit and its frozen ledger. The dated clarifications below use additional linked official documentation and source descriptions; they are not additional native measurements or changes to the archived primary-class counts. In particular, historical class `iii` means freshness for the inspected write/restore path. It does not certify every allowed transition, establish body-plus-field binding on current reads, or prove that an identifier domain is mathematically infinite. Azure snapshot DateTime and the WordPress latest-remaining-revision link require the specific corrections in their platform notes. The six historical `iii` entries must not be reported as six globally publication-fresh current-read identifiers.

## Classification legend

| Code | Meaning |
|---|---|
| **i** | Content-derived: equal content gives an equal identifier, so the identifier returns whenever the content returns. |
| **i\*** | Attribute-derived (an extension of i): the identifier is a function of file attributes such as (mtime, size), not of content. It returns whenever those attributes return, and different content can share it. |
| **ii** | Allocation-unique but reactivatable: each version gets a unique ID, but a documented operation makes an older ID current again. |
| **iii** | Historical fresh-write/restore label: the inspected operation creates a new identifier, or promotes content through a fresh write. A positive continuity claim additionally needs a body-bound current-read field and a complete declared operation scope; this label alone supplies neither. |
| **iv** | Unclear or undocumented. |
| **n/u** | Not unique: the same ID value is reused for different content. This fails uniqueness itself, not only non-reactivation. |
| **n/a** | The feature (versioning, restore) is absent. |

## Findings relevant to the identity non-reactivation argument

1. **Uniqueness is routinely documented together with reactivation.** Several systems describe their identifiers as unique and also document an operation that makes a displaced one current again:
   - S3 "generates a unique version ID", yet "deleting the current version (121212) of an object leaves the previous version (111111) as the current object".
   - B2 calls fileId "The unique identifier for this version of this file", and deleting the latest version restores the older one.
   - Firebase says a version "has a unique identifier", and a rollback re-releases it.
   - npm promises that "that specific name and version combination can never be reused", while `latest` (which npm uses "to identify the current version") can be pointed back at an older version.
   - MediaWiki preserves the "unique rev_id" across undeletion. Full-page restoration can re-expose it after absence, and selective undeletion can make an older rev_id the latest.
2. **Rollback on deploy platforms *is* reactivation.** Netlify ("publishes a previous atomic deploy"), Vercel ("assigning your domains to an existing deployment"), Cloudflare Pages (implied by wording) and Firebase (version ID) implement rollback by re-pointing to an existing identifier. Only Firebase's *release* ID is fresh on rollback.
3. **Fresh allocation on a restore path does not settle current-read continuity.** The inspected GCS, Azure, Firebase release, WordPress restore and ordinary MediaWiki revert paths can allocate new identifiers. Other operations still matter: GCS HNS folder rename preserves generations; MediaWiki full or selective undeletion preserves revision IDs; WordPress revision-row deletion can restore an earlier latest-revision link. A historical selector such as Azure snapshot DateTime also differs from a field attached to the current representation. A positive result requires the operation set, read binding and non-reuse horizon, not just the identifier format or one fresh restore path.
4. **Some "unique" identifiers are not even unique.** Examples are S3's `null` version (same key and version ID before and after a PUT that replaces the content), GCS's `metageneration` (restarts at 1), GCS (name, generation) in HNS buckets ("duplicate soft-deleted objects with identical names and generation values"), and GitHub's `pages_build_version` ("A unique string…", "Default: GITHUB_SHA").
5. **Retention controls do not prevent reactivation.** S3 Object Lock preserves the displaced version, and "Delete markers are not WORM-protected", so placing and then removing a marker re-exposes a locked version with its original ID.
6. **Content- and attribute-derived validators return by construction.** Examples are MD5 ETags (S3, GCS XML, Swift), SHA-1 (B2, MediaWiki `rev_sha1`, Express `res.send`), OCI digests and Git object IDs. They certify content equality, not continuity. Attribute-derived ETags (nginx, Apache default, Express static) return whenever (mtime, size) returns, for example after restoring a file with its mtime preserved. They can also collide across different content.
7. **There are documentation gaps and one contradiction.** Gaps: Wasabi (version semantics), GCS JSON ETag, Azure Undelete ETag, Azure point-in-time restore, R2 single-PUT ETag, GitHub deployment re-activation, and the Ceph and SeaweedFS prose. Contradiction: Swift's object-versioning page says PUT with `version-id` returns 400, while the same page's API docstring, the source and the unit tests implement it as a request whose parameter is the "version to make the latest".

## Per-platform notes

### 1. Amazon S3

- **Identifier on current read:** `x-amz-version-id`, "Version ID of the object." ([GetObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html)), plus ETag and Last-Modified.
- **Uniqueness:** "If you enable versioning for a bucket, Amazon S3 automatically generates a unique version ID for the object that is being stored." and "Only Amazon S3 generates version IDs, and they cannot be edited." ([versioning-workflows](https://docs.aws.amazon.com/AmazonS3/latest/userguide/versioning-workflows.html))
- **Deleting the current version (DeleteObject with versionId):** "When you delete the current object version, you, in effect, turn the previous version into the current version of that object." / "The following figure shows how deleting the current version (121212) of an object leaves the previous version (111111) as the current object." / "A subsequent GET retrieves version 111111." / "After you delete the current version, the previous version becomes the current version." ([RestoringPreviousVersions](https://docs.aws.amazon.com/AmazonS3/latest/userguide/RestoringPreviousVersions.html)). Mechanics: "To remove a specific version, you must use the versionId query parameter. Using this query parameter permanently deletes the version." With MFA Delete: "you must include the x-amz-mfa request header in the DELETE versionId request." ([DeleteObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_DeleteObject.html))
- **Copy restore:** "Amazon S3 supplies a new ID (88778877) and it becomes the current version of the object." (RestoringPreviousVersions). The new ID is fresh.
- **Delete marker removal (undelete):** "To undelete the object, you must delete this delete marker." / "The effect of removing the delete marker is that a simple GET request will now retrieve the current version ID (121212) of the object." ([ManagingDelMarkers](https://docs.aws.amazon.com/AmazonS3/latest/userguide/ManagingDelMarkers.html)). A simple DELETE: "that marker becomes the current version of the object with a new ID." ([DeletingObjectVersions](https://docs.aws.amazon.com/AmazonS3/latest/userguide/DeletingObjectVersions.html))
- **Versioning suspended (`null`):** "After you suspend versioning on a bucket, Amazon S3 automatically adds a null version ID to every subsequent object stored thereafter (using PUT, POST, or CopyObject) in that bucket." / "Although the key and version ID (null) of the null version are the same before and after the PUT, the contents of the null version originally stored in the bucket are replaced by the contents of the object PUT into the bucket." ([AddingObjectstoVersionSuspendedBuckets](https://docs.aws.amazon.com/AmazonS3/latest/userguide/AddingObjectstoVersionSuspendedBuckets.html)). Deletes: "If bucket versioning is suspended, the operation removes the object that has a null versionId. If a version ID exists, Amazon S3 inserts a delete marker that becomes the current version of the object." ([DeletingObjectsfromVersioningSuspendedBuckets](https://docs.aws.amazon.com/AmazonS3/latest/userguide/DeletingObjectsfromVersioningSuspendedBuckets.html)). "To delete a delete marker with a NULL version ID, you must pass the NULL as the version ID in the DeleteObject request." (ManagingDelMarkers). Directory buckets: "Directory buckets - S3 Versioning isn't enabled and supported for directory buckets." (DeleteObject)
- **Object Lock and delete markers:** "Retention periods and legal holds don't prevent new versions of the object from being created, or delete markers to be added on top of the object." / a permanent DELETE of a protected version returns "an Access Denied (403 Forbidden) error" ([object-lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html)). "Although you can't delete a protected object version, you can still create a delete marker for that object." / "Delete markers are not WORM-protected, regardless of any retention period or legal hold in place on the underlying object." ([object-lock-managing](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock-managing.html)). Taken together: Object Lock guarantees that the displaced version survives, and the unprotected delete marker can be removed to make it current again under its original ID.
- **ETag:** "The entity tag is a hash of the object. The ETag reflects changes only to the contents of an object, not its metadata. The ETag may or may not be an MD5 digest of the object data." Objects created by PUT, POST or Copy "encrypted by SSE-S3 or plaintext, have ETags that are an MD5 digest of their object data". "If an object is created by either the Multipart Upload or Part Copy operation, the ETag is not an MD5 digest, regardless of the method of encryption." ([API_Object](https://docs.aws.amazon.com/AmazonS3/latest/API/API_Object.html))
- **Classification:** version ID **ii**; `null` **n/u**; ETag **i** (MD5 case) / **iv** (other cases).

### 2. Google Cloud Storage

- **Identifiers on current read:** XML API `x-goog-generation`, "A response header that indicates which version of the object data you are accessing." ([reference-headers](https://cloud.google.com/storage/docs/xml-api/reference-headers)). JSON `generation`, "The content generation of this object. Used for object versioning and soft delete." ([objects resource](https://cloud.google.com/storage/docs/json_api/v1/objects)). Note: cloud.google.com/storage/docs/* now redirects to docs.cloud.google.com/storage/docs/*.
- **Uniqueness:** "An object version's generation value is unique. A new object with the same name can replace an existing object, but the new object has a different generation value." / "Generation numbers might not increase for future versions, but each new version has a unique generation number." ([metadata](https://cloud.google.com/storage/docs/metadata))
- **Deleting the live version:** "The live version becomes a noncurrent version and keeps the same generation number." Worked example: "Your bucket now contains two noncurrent versions of cat.jpg and no live versions." "Noncurrent versions of objects exist independently of any live version." Deleting the live version by generation: "The live version is permanently deleted." No documented operation promotes a noncurrent version to live in place; restoring is always a copy. ([object-versioning](https://cloud.google.com/storage/docs/object-versioning))
- **Restoring noncurrent:** "In Cloud Storage, restoring a noncurrent object version means making a copy of it. When you do so, the copy becomes the live version, effectively restoring the version." ([using-versioned-objects](https://cloud.google.com/storage/docs/using-versioned-objects)). "A copy of the noncurrent version replaces the live version and receives a new generation number." (object-versioning)
- **Soft-delete restore:** "When you restore a soft-deleted object, Cloud Storage creates a new, live copy of that object within the same bucket." / "When you restore an object, Cloud Storage generates a new version of the object." ([soft-delete](https://cloud.google.com/storage/docs/soft-delete)). "A new generation is assigned and the metageneration is reset to 1." ([objects/restore](https://cloud.google.com/storage/docs/json_api/v1/objects/restore)). Permission condition: "Restoring soft-deleted objects requires specific IAM permissions that are available to the Storage Admin (roles/storage.admin) IAM role." (object-versioning)
- **Move:** the destination gets "A new generation number" and "A new metageneration number, set to 1" ([objects/move](https://cloud.google.com/storage/docs/json_api/v1/objects/move)).
- **HNS folder rename:** "Renaming a folder operates at the folder level, without having to rename every single object. As a result, the creation time of the objects is preserved" ([hns-overview](https://cloud.google.com/storage/docs/hns-overview)). The soft-delete page documents the consequence: "Although rare, duplicate soft-deleted objects with identical names and generation values can occur in buckets with hierarchical namespace enabled. This conflict can happen if you rename folders that contain objects with duplicate names…" Its example ("You rename my-folder-B to my-folder-A. Because of hierarchical namespace, the object's path changes to my-folder-A/cat.png." … "Now, there are two soft-deleted objects named cat.png with the generation number 999.") shows that a folder rename keeps an object's generation. Hence "The restoreToken is only required when the name and generation values of an object do not uniquely identify it." (objects resource; objects/restore). *Inference (flagged):* renaming a folder away and later back re-exposes the same (name, generation) pair as live at the original name, even if another generation was live there in between.
- **metageneration:** "metageneration begins at 1 for each new generation of an object." / "The metageneration property has no meaning without the generation property and should be used only in conjunction with it; it's meaningless to compare metadata generations of two object versions." (metadata)
- **ETag:** "In most cases, users should make no assumptions about the value used in an ETag except that it changes whenever the underlying data or metadata changes, per the specification." / "An object's ETag header returns the object's MD5 value if all the following are true:" "The request is being made through the XML API", Google-managed keys, and a non-composite, non-multipart object. (metadata)
- **Classification:** generation **iii** (flat namespace); (name, generation) in HNS **ii** (inferred; uniqueness explicitly not guaranteed); metageneration **n/u**; ETag **i** (XML MD5) / **iv** (JSON).

### 3. Azure Blob Storage

- **Identifiers:** version ID, ETag, snapshot DateTime. "Each blob version has a unique version ID. The value of the version ID is the timestamp when the blob was updated." / "The version ID stays the same for the lifetime of the version." / "When you perform a write operation to create or modify a blob, Azure Storage returns the x-ms-version-id header in the response." / "After you enable blob versioning for a storage account, every write operation to a blob in that account results in the creation of a new version." - **Deleting the current version:** "When you delete a blob, the current version of the blob becomes a previous version, and there's no longer a current version." (versioning-overview)
- **Restoring a previous version (copy):** "Restoring soft-deleted versions by using the Undelete Blob operation doesn't promote any version to be the current version. To restore the current version, first restore all soft-deleted versions, and then use the Copy Blob operation to copy a previous version to a new current version." / "Undelete never promotes a version to current." (versioning-overview). Portal: "Select the version that you want to promote to be the current version, then select Make current version." / "When versioning is enabled, selecting the Undelete button on a deleted blob restores any soft-deleted versions or snapshots, but does not restore the base blob. To restore the base blob, you must promote a previous version." ([soft-delete-blob-manage](https://learn.microsoft.com/en-us/azure/storage/blobs/soft-delete-blob-manage)). Permission: "Deleting a previous version … deleteBlobVersion/action … Storage Blob Data Owner" (versioning-overview).
- **Soft delete + undelete (versioning off):** "During the retention period, you can restore a soft-deleted object to its state at the time it was deleted." ([soft-delete-blob-overview](https://learn.microsoft.com/en-us/azure/storage/blobs/soft-delete-blob-overview)). "The Undelete Blob operation restores the contents and metadata of a soft-deleted blob, and any associated soft-deleted snapshots." ([Undelete Blob](https://learn.microsoft.com/en-us/rest/api/storageservices/undelete-blob)). Whether the restored blob carries its pre-deletion ETag is **not documented (iv)**.
- **Snapshots:** "When you create a snapshot of a blob, the blob's system properties are copied to the snapshot with the same values." / "Because you can't modify a snapshot, you restore a base blob by copying a snapshot over it." - **ETag:** "Azure Storage assigns an identifier to every object stored. This identifier is updated every time a write operation is performed on an object. The identifier is returned to the client as part of an HTTP GET response in the ETag header defined by the HTTP protocol." ([concurrency-manage](https://learn.microsoft.com/en-us/azure/storage/blobs/concurrency-manage)). Copy-based restores are writes, so the ETag is fresh.
- **Point-in-time restore:** "The effect is to revert write and delete operations that happened during the retention period." / "Only the base blob (current version) is restored to its previous state." ([point-in-time-restore-overview](https://learn.microsoft.com/en-us/azure/storage/blobs/point-in-time-restore-overview)). With revisions enabled, the relevant rows retained, permission to read edit-context content and delete revisions, and no concurrent update or plugin alteration of these core paths, the scoped observation `(content.raw, predecessor-version.id)` admits `A/r1 → edit B/r2 → restore A/r3 → delete r3 and r2 → A/r1`. - **Classification: iii** remains the historical restore-path label; it is not a positive continuity certificate for the larger operation set including revision deletion.

The source ([ngx_http_core_module.c](https://github.com/nginx/nginx/blob/master/src/http/ngx_http_core_module.c)) uses `etag->value.len = ngx_sprintf(etag->value.data, "\"%xT-%xO\"",` with `r->headers_out.last_modified_time,` and `r->headers_out.content_length_n)`. The ETag is therefore hex mtime (seconds) and hex length: **i\***.
- **Apache httpd:** "File attributes used to create the ETag HTTP response header for static files". "Default: FileETag MTime Size". "Compatibility: The default used to be "INode MTime Size" in 2.3.14 and earlier." The `Digest` keyword: "If a document is file-based, the ETag field will be calculated by taking the digest over the file." ([FileETag](https://httpd.apache.org/docs/2.4/mod/core.html#fileetag)). Default **i\***; `Digest` **i**.
- **Express / etag:**
  - App setting: "true enables weak ETag. This is the default setting. false disables ETag altogether." / "These settings apply only to dynamic files, not static files. The express.static middleware ignores these settings." ([Express 5.x application](https://expressjs.com/en/5x/api/application/))
  - `res.send` uses `var etagFn = app.get('etag fn')` and `if ((etag = etagFn(chunk, encoding))) {` ([response.js](https://github.com/expressjs/express/blob/master/lib/response.js)).
  - The etag package: "Generate a strong ETag for the given entity. This should be the complete body of the entity. Strings, `Buffer`s, and `fs.Stats` are accepted. By default, a strong ETag is generated except for `fs.Stats`, which will generate a weak ETag (this can be overwritten by `options.weak`)." ([etag README](https://github.com/jshttp/etag/blob/master/README.md)). For entities it computes `.createHash('sha1')` and `return '"' + len.toString(16) + '-' + hash + '"'`. For stats it computes `var mtime = stat.mtime.getTime().toString(16)` and `return '"' + size + '-' + mtime + '"'` ([index.js](https://github.com/jshttp/etag/blob/master/index.js)).
  - Static files: send uses `var val = etag(stat)` ([send](https://github.com/pillarjs/send/blob/master/index.js)). serve-static says: "Enable or disable etag generation, defaults to true." ([serve-static](https://expressjs.com/en/resources/middleware/serve-static/))
  - Result: `res.send` **i** (content hash); static **i\*** (size and mtime).

## Limitations

- These are documentation-level findings. No behaviour was tested against live services.
- Original primary-class counts are preserved for reproducibility; the scope corrections above supersede any universal interpretation of `iii`. Historical-object selectors and management-event IDs require a demonstrated binding to current content before use as current-read evidence.
- No entry establishes an infinite production identifier domain. For example, GCS exposes `generation` as a `long` ([Object schema](https://docs.cloud.google.com/storage/docs/json_api/v1/objects), [integer formats](https://docs.cloud.google.com/docs/discovery/type-format)), and MediaWiki uses a finite integer revision ID ([revision table](https://www.mediawiki.org/wiki/Manual:Revision_table/en)). Positive engineering claims assume non-reuse within a stated operation scope and certification horizon, with exhaustion/reset behavior accounted for.
- Several classifications rest on project source or test code rather than prose: Ceph (s3-tests), Swift new-mode `PUT ?version-id`, SeaweedFS, WordPress, the MediaWiki undelete mechanics, and the nginx ETag format. These are labelled where they occur.
- GCS-HNS (reactivation by rename-back) and Cloudflare Pages (ID reuse) are inferences from documented semantics and are marked as such.
- Vendor documentation changes. The SHA-256 of every local copy is in the JSON ledger, so each quote can be re-checked against the exact text that was audited.
